# 5. Problems Found & Key Decisions

สรุปปัญหาที่พบระหว่างทำ สิ่งที่ทีมตัดสินใจ และเหตุผล (ขอบเขตปัจจุบัน: จังหวัดเชียงใหม่) รายละเอียดเชิงลึกอยู่ในเอกสารที่อ้างอิงท้ายแต่ละข้อ

## 5.1 การเปลี่ยนขอบเขตและคำถามวิจัย

| ปัญหาที่พบ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| ข้อมูลชุดแรก 8 ไฟล์อยู่คนละจังหวัด (หนองคาย พังงา ยโสธร) คนละระดับพื้นที่ (หมู่บ้านถึงภาค) และปีแทบไม่ซ้อนกัน integrate ได้ตารางที่ใช้จริงเพียง 10 แถว | เปลี่ยนเป็นข้อมูล 5 ไฟล์ของจังหวัดเชียงใหม่ที่ใช้รหัส/ชื่อหมู่บ้านร่วมกัน ย้ายงานเดิมไปไว้ใน `transformation/backup/` และ `ingestion/data_backup_20261123/` | ต้องเชื่อมข้อมูลได้จริงถึงจะตอบคำถามได้ |
| ไม่มีข้อมูลการฟื้นตัวและระดับน้ำในทุกแหล่ง | ตัดคำถามเรื่องการฟื้นตัว ปรับคำถามเป็น Q1–Q3 ชุดเชียงใหม่ | ไม่ตั้งคำถามที่ข้อมูลตอบไม่ได้ |

อ้างอิง: `docs/01-problem-and-systems-thinking.md` หัวข้อ 1.3, `data_catalog/sources.md` หัวข้อ 6

## 5.2 ปัญหาด้านข้อมูล

| ปัญหาที่พบ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| ข้อมูลอุทกภัยสองปีใช้ชื่อคอลัมน์และรูปแบบวันที่ต่างกัน และแถวที่ 2 เป็นคำอธิบายหัวตารางภาษาไทย | แมปเป็นชื่อมาตรฐานชุดเดียวกันก่อนรวม แถวคำอธิบายถูก quarantine | รวมสองปีได้โดยยังแยกปีต้นทาง (`source_year`) |
| flood เป็นข้อมูลทั้งประเทศ (19,584 / 34,875 แถว) | คัดเฉพาะจังหวัดเชียงใหม่ (1,198 / 3,556 แถว) | ตรงกับขอบเขตการศึกษา |
| `Affected People` / `Affected Households` ว่างเป็นส่วนใหญ่ (เชียงใหม่มี `affected_households` แค่ 15.9% ปี 2566 และ 6.1% ปี 2567) | ไม่เติม 0 และใช้ "จำนวนหมู่บ้านที่ถูกรายงาน" เป็นตัวชี้วัดหลักของ Q1–Q3 | ค่าว่างไม่ได้แปลว่าไม่มีผลกระทบ |
| 6 แถวในปี 2567 รหัสตำบลไม่ตรงอำเภอ และ 13 รหัสหมู่บ้าน (33 แถว) ไม่พบใน village mapping | แถวรหัสผิด quarantine ส่วนแถวที่ไม่พบรหัสเก็บไว้แบบ unmatched (`village_found = false`) | ไม่ทิ้งรายงานอุทกภัยจริง และไม่เดาหมู่บ้าน |
| `chiangmai_damage.xlsx` มีแถวซ้ำทุกคอลัมน์ 17 แถว และ key ซ้ำแต่ค่าต่าง 16 แถว | แถวซ้ำทุกคอลัมน์ quarantine ส่วน key ซ้ำเก็บไว้และติด `source_record_id` | พื้นที่เดียวกันอาจมีหลายรายงานจริง |
| damage ใช้เลขตำบล/หมู่บ้านแบบท้องถิ่น ไม่ใช่รหัสมาตรฐาน | เชื่อมกับหมู่บ้านแค่ระดับอำเภอ (`district_code`) | เชื่อมระดับหมู่บ้านแล้วเสี่ยงจับคู่ผิดพื้นที่ |
| `household_income.xlsx` ไม่มีรหัสหมู่บ้าน และ 13 แถวรายได้ต่ำกว่า 1,000 บาท (น่าจะเป็นหน่วยพันบาท) | จับคู่ด้วยชื่อ อำเภอ + ตำบล + พื้นที่ เฉพาะกรณีที่ตรงหมู่บ้านเดียว (unique 67.22%) แถวรายได้ผิดหน่วย quarantine | ไม่บังคับจับคู่และไม่เดาหน่วย ใน Q3 หมู่บ้านที่ไม่มีรายได้ใช้ค่ากลาง 0.5 พร้อมธง `income_available` |
| `village_mapping.json` มีพิกัดผิดหรืออยู่นอกเชียงใหม่ 14 แถว | quarantine | พิกัดผิดทำให้ตีความพื้นที่ผิด |
| ไฟล์ damage, income, village mapping ไม่มีลิงก์สาธารณะ | ระบุว่าเป็นไฟล์ที่ทีมได้รับโดยตรง บันทึกเนื้อหา ช่วงเวลา และข้อจำกัดตามไฟล์จริง และ commit ข้อมูลหลัง validation ไว้ใน `validation/cleaned/` | ผู้ตรวจตรวจสอบและรัน pipeline ซ้ำได้แม้ไม่มีไฟล์ดิบ |

## 5.3 ปัญหาด้านการรันและวิธีแก้

| ปัญหาที่พบ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| ข้อมูลดิบไม่อยู่ใน Git ทำให้คนนอกทีมรัน validation ไม่ได้ | `run_all.py` เริ่มจาก `validation/cleaned/` เป็นค่าเริ่มต้น และใช้ `--from-raw` เมื่อมีไฟล์ดิบ | รัน transformation → storage → query ได้ทันทีด้วยคำสั่งเดียว |
| Lambda ต้องอ่านไฟล์ตามโครงสร้าง S3 (`raw/...`) แต่ในเครื่องเก็บไฟล์ไว้ที่ `ingestion/data/` | `prepare_local_data.py` คัดลอกไฟล์ไปตามโครงสร้างที่ต้องการ โดยอ่านการแมปจาก `ingestion/config.py` | ใช้โค้ดชุดเดียวกันทั้งในเครื่องและบน Lambda |
| ไฟล์ Parquet ที่รันซ้ำมีไบต์ต่างจากเดิมแม้ข้อมูลเหมือนกัน | เทียบด้วยการอ่านข้อมูลเป็น DataFrame ไม่เทียบ checksum | metadata ของไฟล์ขึ้นกับเวอร์ชันไลบรารี ไม่ใช่เนื้อหาข้อมูล |
| ทดสอบ query บน Athena ทุกครั้งมีค่าใช้จ่ายและต้องใช้ credentials | `storage/run_local_queries.py` รัน SQL ชุดเดียวกันด้วย DuckDB แล้วเทียบผลกับ Athena | ตรวจผลได้โดยไม่ต้องใช้ AWS |

## 5.4 การตัดสินใจด้านสถาปัตยกรรม

| การตัดสินใจ | เหตุผล |
|---|---|
| เก็บข้อมูลดิบไว้ครบ ไม่แก้ raw และแยกผลตรวจเป็น `reports/`, `cleaned/`, `quarantine/` | ตรวจสอบย้อนหลังได้ว่าแถวใดถูกตัดและเพราะอะไร |
| `ingest.py` เทียบ md5 ก่อนอัปโหลดและเขียน manifest (ที่มา, ลิงก์, ช่วงเวลา) | รันซ้ำได้โดยไม่อัปโหลดซ้ำ และมีหลักฐานที่มาของข้อมูล |
| Step Functions ขั้นแรก `CheckBatch` ตรวจไฟล์ `_SUCCESS.json` ของ batch นั้น | ป้องกันการประมวลผล batch เดิมซ้ำ |
| Transformation เขียนเป็น CSV ส่วน Curated Zone เป็น Parquet แบบ star schema แบ่ง partition ตาม `source_year` | CSV อ่านตรวจง่าย Parquet ให้ Athena อ่านเร็วและ prune partition ได้ |
| ลงทะเบียนตารางด้วย DDL ที่ generate จาก `storage/schema.py` และใช้ partition projection | ชนิดข้อมูลในไฟล์กับใน Glue Catalog ตรงกันเสมอ และไม่ต้องลงทะเบียน partition เองเมื่อมีปีใหม่ (docs/06 D5–D6) |
| ใช้ Lambda และ Step Functions ห่อสคริปต์เดิมโดยไม่แก้สคริปต์ (`orchestration/lambda_handlers.py`) | โค้ดชุดเดียวกันทำงานได้ทั้งในเครื่องและบน AWS |
| สถานะปัจจุบัน: ขั้น Curated และ Query ยังรันด้วยมือหลัง batch สำเร็จ ไม่อยู่ใน Step Functions | แสดงไว้ในแผนภาพให้ชัด งานต่อคือเพิ่มเป็น state หลัง `VerifyBatch` (README ข้อ 9) |

อ้างอิง: `docs/06-storage-data-model-query.md` หัวข้อ 3, `orchestration/README.md`, แผนภาพใน `README.md`
