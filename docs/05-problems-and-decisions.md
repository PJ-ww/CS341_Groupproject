# 5. Problems Found & Key Decisions

สรุปปัญหาที่พบระหว่างทำ สิ่งที่ทีมตัดสินใจ และเหตุผล เพื่อใช้ประกอบการอธิบาย Pipeline รายละเอียดเชิงลึกอยู่ในเอกสารที่อ้างอิงท้ายแต่ละข้อ

## 5.1 ปัญหาด้านข้อมูล

| ปัญหาที่พบ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| `Geographic_Data.csv` มีแถวซ้ำตรงกันทุกคอลัมน์ 44 แถว (2 กลุ่ม กลุ่มละ 23 occurrence) จาก 1,816 แถว | เก็บ occurrence แรกไว้ ได้ 1,772 แถวใน `validation/cleaned/Geographic_Data_deduplicated.csv` และเก็บ 44 แถวซ้ำไว้ใน `validation/quarantine/` | ไม่แก้ raw และเก็บหลักฐานไว้ตรวจสอบ ใช้สำเนาที่ตัดซ้ำเป็น input ของ transformation |
| `2564_by_disaster_type1.csv` เป็นรายงานสรุป มีแถวหัวตารางต่อ แถวสรุป และรายการที่ไม่ใช่จังหวัดปะปน (83 แถว) | ใช้เฉพาะ 76 แถวของจังหวัด (ส่วน "วงเงินจังหวัด") อีก 7 แถวแยกเข้า quarantine | ต้องการตารางระดับจังหวัดที่ไม่ปนแถวสรุป ไม่ให้ยอดรวมนับซ้ำ |
| ค่า `-` และ `--` ในไฟล์งบประมาณ | แปลงเป็นค่าว่าง (missing) ไม่ใช่ 0 | ต้นทางไม่ได้ยืนยันว่าหมายถึงศูนย์ การใส่ 0 อาจทำให้สรุปผิด |
| ช่องปีว่างในข้อมูลสถิติอุทกภัยรายหมู่บ้าน (57,024 แถว) | เก็บเป็น missing และสร้าง `years_with_reported_value` | ว่างอาจหมายถึงไม่มีเหตุการณ์หรือไม่มีการรายงาน จึงไม่เติม 0 |
| ข้อมูลรายได้ NSO เป็นระดับจังหวัดแยกตามกลุ่มเศรษฐกิจ ไม่ใช่ระดับครัวเรือน | ไม่รวมกลุ่ม และเชื่อมกับข้อมูลภูมิศาสตร์เฉพาะระดับจังหวัด-ปี (ยโสธร ปี 2568) ได้ตาราง `geographic_nso_integrated` 10 แถว | ความละเอียดของข้อมูลไม่เท่ากัน จึงตีความเป็นบริบทระดับจังหวัดเท่านั้น |
| ข้อมูลครัวเรือนที่ได้รับผลกระทบเป็นของจังหวัดพังงา ส่วนข้อมูลภูมิศาสตร์เป็นของยโสธร | ไม่ join ข้อมูลสองชุดนี้ | พื้นที่ไม่ตรงกัน การ join จะให้ผลที่ไม่มีความหมาย |
| `Number_of_Affected_Households.xlsx` มี 3 หน่วย (ตำบล หมู่บ้าน ครัวเรือน) และไม่ระบุปี | ไม่รวมยอดข้ามหน่วย และไม่สร้างคอลัมน์ปี | การรวมต่างหน่วยทำให้ตัวเลขผิดความหมาย |
| `pdpm_gd015.csv` ซ้อนกับสถิติอุทกภัยรายหมู่บ้านและไม่มีค่าปีที่ไม่ว่างเพิ่ม | ไม่ใช้เป็นแหล่งเสริม (ยังตรวจใน validation) | ไม่เพิ่มข้อมูลใหม่ |

อ้างอิง: `docs/04-data-validation.md`, `docs/data-quality-summary.md`, `transformation/README.md` หัวข้อ 5–7

## 5.2 ปัญหาด้านการรันและวิธีแก้

| ปัญหาที่พบ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| สคริปต์ transformation 5 ตัวอ่านข้อมูลดิบจาก `ingestion/data/raw/...` (โครงสร้างเดียวกับ S3 และโฟลเดอร์ทำงานของ Lambda) แต่ผู้ใช้ดาวน์โหลดไฟล์ไว้ที่ `ingestion/data/` ทำให้รันในเครื่องไม่ผ่าน (`FileNotFoundError`) | เพิ่ม `prepare_local_data.py` คัดลอกไฟล์ไปตามโครงสร้างที่ต้องการ โดยอ่านการแมปจาก `ingestion/config.py` | ไม่แก้ path ในสคริปต์เพื่อให้ Lambda ใช้โค้ดชุดเดียวกับที่รันในเครื่องได้ไม่เปลี่ยน |
| ลำดับคำสั่งใน README ขาด `integrate_data.py` และ `requirements.txt` ขาด `openpyxl` | เพิ่มทั้งสองรายการ และเพิ่ม `run_all.py` รันทุกขั้นตามลำดับพร้อมตรวจจำนวนแถว | ลดความผิดพลาดจากการพิมพ์คำสั่งเอง และพิสูจน์ได้ว่าผลตรงกับที่รายงาน |
| ไฟล์ Parquet ที่รันซ้ำมีไบต์ต่างจากเดิมแม้ข้อมูลเหมือนกัน (metadata ของไฟล์ต่างกันตามเวอร์ชันไลบรารีหรือสภาพแวดล้อม) | เทียบด้วยการอ่านข้อมูลเป็น DataFrame ไม่เทียบ checksum | metadata ของไฟล์ขึ้นกับเวอร์ชันไลบรารี ไม่ใช่เนื้อหาข้อมูล |

## 5.3 การตัดสินใจด้านสถาปัตยกรรม

| การตัดสินใจ | เหตุผล |
|---|---|
| เก็บข้อมูลดิบไว้ครบ ไม่แก้ raw และแยกผลตรวจเป็น `reports/`, `cleaned/`, `quarantine/` | ตรวจสอบย้อนหลังได้ว่าแถวใดถูกตัดและเพราะอะไร |
| `ingest.py` เทียบ md5 ก่อนอัปโหลดและข้ามไฟล์ที่ไม่เปลี่ยน | รันซ้ำได้โดยไม่อัปโหลดซ้ำ (idempotent) |
| Step Functions ขั้นแรก `CheckBatch` ตรวจไฟล์ `_SUCCESS.json` ของ batch นั้น | ป้องกันการประมวลผล batch เดิมซ้ำ |
| เขียนผลลัพธ์เป็นทั้ง CSV และ Parquet | CSV ไว้ตรวจดู Parquet ไว้ให้ Athena ค้นหา |
| ใช้ Lambda และ Step Functions ห่อสคริปต์เดิมโดยไม่แก้สคริปต์ (`orchestration/lambda_handlers.py`) | โค้ดชุดเดียวกันทำงานได้ทั้งในเครื่องและบน AWS |

อ้างอิง: `docs/02-initial-data-architecture.md`, `docs/data-model.md`, `orchestration/`
