# 4. Data Validation & Data Quality

## 4.1 วิธีตรวจ

ใช้ `ingestion/validate_data.py` ตรวจ CSV และ XLSX ใน `ingestion/data/` โดยไม่เขียนทับข้อมูลต้นฉบับ ตัวตรวจเช็กจำนวนคอลัมน์, ฟิลด์หลักตามชุดข้อมูล, รูปแบบปี/ตัวเลข/หน่วย และแถวซ้ำที่ตรงกันทุกคอลัมน์ ผลลัพธ์แยกไว้ในโฟลเดอร์ `validation/` ที่ root ของ repo ดังนี้:

- `reports/validation_report.json`: รายงานภาพรวมและสถิติรายคอลัมน์
- `cleaned/`: ข้อมูลที่จัดการแล้วสำหรับนำไปวิเคราะห์
- `quarantine/`: แถวที่ถูกแยก พร้อมเลขแถวต้นฉบับและเหตุผล

สำหรับ Geographic จะสร้างสำเนาที่ตัดแถวซ้ำเพื่อใช้วิเคราะห์ที่ `validation/cleaned/Geographic_Data_deduplicated.csv` โดยเก็บ raw เดิมไว้ครบ

รันซ้ำหลังแก้กฎหรือมีไฟล์ชุดใหม่ได้จาก root ของ repo:

```powershell
python ingestion/validate_data.py
```

ตัวตรวจใช้ Python standard library จึงไม่ต้องติดตั้ง dependency เพิ่ม

## 4.3 ข้อสังเกตที่ต้องยืนยันกับเจ้าของชุดข้อมูล

- `Geographic_Data.csv` มีข้อมูลซ้ำตรงกันทุกคอลัมน์จริง 2 กลุ่ม กลุ่มละ 23 occurrence (ปี 2567 และ 2568); จึงเก็บไว้กลุ่มละ 1 แถวในสำเนาสะอาด และแยก occurrence ซ้ำ 44 แถวออกจากสำเนานั้น โดย raw ไม่ถูกแก้ไข
- หัวคอลัมน์ `เหล่งที่มา` ในไฟล์เดียวกันอาจสะกดคลาดเคลื่อนจาก `แหล่งที่มา`; ยังไม่เปลี่ยนชื่อใน raw
- `2564_by_disaster_type1.csv` เป็นรายงานสรุป ไม่ใช่ตารางข้อมูลแบบแบนทั้งหมด แถวที่ถูกแยกมีทั้งแถวต่อหัวตาราง สรุปวงเงิน และรายการระดับหน่วยงาน จึงควรใช้เฉพาะ 76 แถวจังหวัดเมื่อนำไปวิเคราะห์ระดับจังหวัด
- ช่องว่างในคอลัมน์ปีของข้อมูล ปภ. และช่องว่างใน `หมู่ที่` ของ Geographic ไม่ถูกแทนด้วยศูนย์ เพราะความหมายอาจเป็นไม่มีเหตุการณ์หรือไม่มีรายละเอียดระดับหมู่บ้าน

## 4.4 ข้อจำกัด

กฎตรวจยืนยันความครบถ้วนพื้นฐานและรูปแบบที่ระบุได้จากไฟล์เท่านั้น ยังไม่ได้ยืนยันคำจำกัดความเชิงธุรกิจกับหน่วยงานต้นทาง และยังไม่ได้ตรวจความสอดคล้องของยอดรวมรายจังหวัดกับเอกสารต้นฉบับ แถว quarantine จึงหมายถึงต้องตรวจเพิ่ม ไม่ใช่ข้อสรุปว่าแหล่งข้อมูลผิด
